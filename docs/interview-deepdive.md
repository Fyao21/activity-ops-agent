# 智能课程学习助手 Agent 平台 面试官追问版

这份文档整理面试官容易深挖的问题，重点放在：

- RAG 知识库
- Text-to-SQL 与 SQL Guard
- Hybrid Agent
- Java 调 Python
- RocketMQ 异步任务
- 幂等、一致性和可排障设计

---

## 1. RAG 知识库相关追问

### Q1：为什么这个项目需要 RAG，而不是直接把问题丢给大模型？

A：

课程学习场景里，回答必须尽量基于课程资料。如果直接让大模型回答，它可能会凭通用知识生成看起来合理但和本课程资料不一致的内容。

所以我使用 RAG：先从课程资料向量库检索相关片段，再把片段和问题一起交给大模型，并在 Prompt 中约束“只能基于给定上下文回答”。这样可以降低幻觉，也能让答案更贴近课程资料。

---

### Q2：课程资料上传后的完整索引流程是什么？

A：

流程是：

1. 用户调用 `/knowledge/upload` 上传 `txt` 或 `md` 文件。
2. Java 后端校验课程存在、文件非空、扩展名合法。
3. 文件保存到 `uploads/knowledge`。
4. MySQL 写入 `knowledge_document`，状态是待处理。
5. 后端发送 `edu_knowledge_index_topic:DOC_INDEX` 消息。
6. `KnowledgeIndexConsumer` 消费消息并调用 Python `/rag/index`。
7. Python 读取文件、文本切分、Embedding 向量化并写入 FAISS。
8. Java 保存 `knowledge_chunk` 元数据。
9. 更新文档状态为成功；失败时写入失败原因。

这个设计避免了上传接口被文档解析和向量化阻塞。

---

### Q3：文档索引为什么要异步？

A：

文档索引涉及文件读取、文本切分、Embedding 模型调用和向量入库，耗时不稳定。如果同步处理，上传接口会变慢，甚至因为 Python 服务或模型接口波动导致上传失败。

异步化以后，上传接口只保证文件和元数据保存成功，然后把索引任务交给 RocketMQ 消费者处理。这样主流程响应更快，也能利用 RocketMQ 的重试能力提升可靠性。

---

### Q4：RAG 索引重复消费怎么办？

A：

我在消费者里做了两层幂等：

1. 如果 `knowledge_document.status` 已经是成功，直接跳过。
2. 重新保存切片前，先按 `document_id` 删除旧的 `knowledge_chunk`，再插入新切片。

这样即使 RocketMQ 重复投递，也不会无限追加重复切片。

---

## 2. Text-to-SQL 与 SQL Guard 相关追问

### Q5：为什么 Text-to-SQL 一定要做 SQL Guard？

A：

因为模型生成的 SQL 不一定可靠。它可能生成修改数据的语句、多语句、访问敏感字段，或者扫描过大的结果集。

Text-to-SQL 不能只关注“能不能查出来”，还要关注“能不能安全地查”。所以我在执行 SQL 前加了 SQL Guard。

---

### Q6：SQL Guard 具体做了哪些限制？

A：

主要有这些：

1. 去掉模型可能返回的 Markdown SQL 代码块。
2. 只允许 `SELECT` 开头。
3. 禁止多语句执行。
4. 禁止 `INSERT / UPDATE / DELETE / DROP / ALTER / TRUNCATE / CREATE / REPLACE / MERGE / CALL / GRANT / REVOKE` 等危险关键字。
5. 禁止访问 `password` 字段。
6. 限制只能访问白名单表，比如 `course`、`knowledge_document`、`agent_qa_record`、`learning_event`、`question`、`answer_record`。
7. 没有 `LIMIT` 时自动补 `LIMIT 100`。

这些限制能把模型查询控制在只读、有限、可审计的范围内。

---

### Q7：为什么要做表白名单？

A：

只禁止危险关键字还不够，因为模型可能查询和当前场景无关的表，或者访问系统内部表。表白名单可以明确告诉系统哪些表是教学数据分析允许访问的。

这个项目里 SQL 查询主要服务于课程、资料、问答、学习行为、题目和答题分析，所以只开放这些必要表，减少数据泄露面。

---

### Q8：自动补 `LIMIT 100` 的意义是什么？

A：

主要是控制结果集规模。如果模型生成不带限制的查询，可能导致数据库慢查询，也会让大模型总结阶段处理过多数据，接口响应变慢。

默认补 `LIMIT 100` 是一道兜底保护。

---

## 3. Hybrid Agent 相关追问

### Q9：Hybrid Agent 解决什么问题？

A：

有些问题只查资料不够，只查数据库也不够。例如“结合 Redis 课程资料和最近错题情况，分析学生薄弱点”。

这种问题需要两类信息：

- RAG 提供课程资料里的知识点内容。
- Text-to-SQL 提供学生答题、错题、学习行为等数据。

Hybrid Agent 会把两边结果合并，再让大模型生成综合分析和复习建议。

---

### Q10：问题路由是怎么做的？

A：

Python 侧有一个 `question_router.py`，按关键词判断问题类型：

- 包含“统计、数量、正确率、排名、最近、平均、活跃度”等，更偏 SQL。
- 包含“什么是、解释、原理、总结、复习、资料、文档”等，更偏 RAG。
- 包含“结合、根据、分析、建议、薄弱点、掌握情况”等，走 Hybrid。

如果同时命中 SQL 和 RAG，或者明显是综合分析类问题，就走 Hybrid。这样前端只需要调用统一的 `/agent/query`。

---

### Q11：关键词路由有什么不足，后续怎么优化？

A：

关键词路由实现简单、可解释，适合项目早期验证，但它对复杂表达和歧义问题不够稳。

后续可以优化为：

1. 增加规则优先级和领域词库。
2. 用少量样例做意图分类 Prompt。
3. 保存路由结果和用户反馈，用于评估路由准确率。
4. 对低置信度问题返回澄清提示。

---

## 4. Java 调 Python 相关追问

### Q12：为什么拆成 Java 后端和 Python Agent 两个服务？

A：

Java 更适合承接标准业务系统，比如课程、题目、答题、数据库事务、缓存、MQ 和权限。Python 在 LangChain、RAG、Embedding、FAISS、大模型调用方面生态更成熟。

拆成两个服务以后，职责清晰：

- Java 做业务主系统。
- Python 做 AI 能力服务。

后续升级 Agent、替换模型、调整向量库时，也不会影响 Java 业务主体。

---

### Q13：Java 调 Python 失败怎么办？

A：

当前 Java 侧通过客户端封装 Python 调用，异常会转成业务异常，不把底层堆栈暴露给前端。同时，问答记录会保存成功失败状态和错误信息，便于排查。

如果继续增强，我会补：

1. 调用超时和重试策略。
2. 熔断降级。
3. Python 服务健康检查。
4. 调用链日志和告警。

---

### Q14：为什么要保存 Agent 问答记录？

A：

Agent 类项目最难排查的问题通常不是普通接口异常，而是模型生成的 SQL、检索上下文或最终回答不符合预期。

所以我把 `question`、`route_type`、`generated_sql`、`retrieved_context`、`answer`、`success`、`error_message` 保存到 `agent_qa_record`。这样可以复盘模型行为、排查用户反馈、优化 Prompt，也方便后续做问答历史和审计。

---

## 5. RocketMQ 与异步任务相关追问

### Q15：项目里 RocketMQ 用在哪些场景？

A：

主要有三类：

1. 文档索引：`edu_knowledge_index_topic`，上传资料后异步调用 Python RAG 建索引。
2. 学习行为：`edu_learning_event_topic`，记录提问、答题、查看课程、上传资料等行为。
3. 答题统计：`edu_answer_stat_topic`，提交答案后发送统计任务，为后续课程统计和知识点统计预留。

---

### Q16：为什么学习行为也要异步？

A：

学习行为可能非常高频，比如查看课程、提问、答题。如果每次都同步写统计或扩展画像，会增加主接口耗时。

异步以后，主流程只发消息，消费者再落库或更新统计。这样业务解耦，也方便后续增加推荐、画像、活跃度统计等下游任务。

---

### Q17：RocketMQ 消费失败后怎么处理？

A：

消费者处理成功就正常返回；如果处理失败，记录日志并抛出异常，让 RocketMQ 按策略重试。

文档索引场景里，消费者还会把失败原因写入 `knowledge_document.error_message`，前端或排查人员可以看到文档为什么失败。

后续可以继续补充消费失败告警、死信队列巡检和补偿消费。

---

### Q18：项目里怎么处理重复消费？

A：

不同任务用不同业务键做幂等：

- 文档索引：通过 `knowledge_document.status` 判断是否已成功，重建切片前删除旧切片。
- 学习行为：通过 `messageKey` 判断是否已消费，数据库唯一键防重复写入。
- 答题统计：当前按 `answerRecordId` 做重复消费保护，后续可扩展为数据库幂等表或统计状态字段。

---

## 6. 项目困难、难点和解决方案

### Q19：项目中你遇到的最大困难是什么？

A：

我会讲四个：

1. 文档索引耗时不稳定。解决方式是 RocketMQ 异步索引，上传接口只保存文件和发消息。
2. 模型 SQL 有安全风险。解决方式是 SQL Guard，从只读、多语句、危险关键字、敏感字段、表白名单和 `LIMIT` 做限制。
3. RAG、SQL、Hybrid 链路差异大。解决方式是统一 `/agent/query` 入口，通过路由器分发到不同处理链路。
4. 消息重复消费会造成重复写入。解决方式是按业务唯一标识做幂等。

---

### Q20：这个项目最能体现工程能力的地方是什么？

A：

我认为不是单纯接了大模型 API，而是把 Agent 能力工程化落到了业务系统里：

- 有 Java/Python 服务边界。
- 有 RAG 检索和 SQL 查询两套能力。
- 有 SQL Guard 安全兜底。
- 有 RocketMQ 异步任务和幂等设计。
- 有问答记录、错误状态和文档状态，便于排障。

---

## 7. 当前不足与优化方向

### 当前不足

1. 登录后还需要补更完整的 token 鉴权、角色权限和数据权限。
2. 文档类型目前主要支持 `txt` 和 `md`，还可以扩展 PDF、DOCX、PPTX。
3. 问题路由还是规则关键词，复杂语义下准确率需要评估。
4. RocketMQ 已有重试能力，但告警、死信队列巡检和补偿消费还不够完整。
5. Agent 侧缺少系统化评测集和链路监控。

### 后续优化

1. 增加 Spring 拦截器和角色权限控制。
2. 扩展文档解析能力和大文件分片处理。
3. 优化路由为规则加模型分类的组合方案。
4. 完善 MQ 失败告警、DLQ 巡检和补偿任务。
5. 增加 RAG 命中率、SQL 成功率、模型调用耗时等监控指标。

---

## 8. 一句话总结

这个项目最大的价值在于，我不只是做了课程、题目、答题这些普通业务接口，还把 RAG、Text-to-SQL、Hybrid Agent、SQL 安全、RocketMQ 异步任务和幂等排障这些工程化问题串成了一个完整的智能学习平台。
