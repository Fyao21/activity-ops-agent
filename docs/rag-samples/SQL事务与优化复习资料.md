# SQL 事务与优化复习资料

## 事务 ACID

事务是数据库保证一组操作作为整体执行的机制。ACID 分别表示原子性、一致性、隔离性和持久性。原子性表示事务中的操作要么全部成功，要么全部失败；一致性表示事务执行前后数据满足约束；隔离性表示多个事务并发执行时相互影响受隔离级别控制；持久性表示事务提交后数据即使宕机也不应丢失。

在业务系统中，创建订单、扣库存、保存答题记录、保存文档元数据等都可能涉及事务。事务边界要围绕业务一致性设计，而不是简单把所有代码都放进一个事务。事务太小可能无法保证一致性，事务太大又会持锁时间过长，降低并发。

课程学习助手中，答题提交需要先校验用户、课程和题目，再保存 answer_record。保存成功后发送学习行为和答题统计消息。严格来说，数据库写入和消息发送之间存在一致性边界，生产环境可以用本地消息表或事务消息增强。

## 事务隔离级别

常见隔离级别包括读未提交、读已提交、可重复读和串行化。读未提交可能读到其他事务未提交数据，几乎不用。读已提交解决脏读，但同一事务内多次读取同一数据可能结果不同。可重复读解决不可重复读，是 MySQL InnoDB 默认隔离级别。串行化隔离最强，但并发能力最差。

并发问题包括脏读、不可重复读和幻读。脏读是读到未提交数据；不可重复读是同一行数据前后读取不一致；幻读是同一范围查询前后出现新增或删除的记录。InnoDB 在可重复读下通过 MVCC 和 Next-Key Lock 在很多场景下避免幻读。

选择隔离级别要结合业务。大多数互联网业务使用 MySQL 默认可重复读即可。报表查询和统计分析通常更关注性能和结果可接受性，不一定需要强隔离。核心资金类业务需要更严格的事务和锁控制。

## MVCC

MVCC 是多版本并发控制，让读操作不阻塞写操作，写操作也尽量不阻塞读操作。InnoDB 每行记录有隐藏字段，包括事务 ID 和回滚指针。事务读取数据时会基于 Read View 判断哪个版本对当前事务可见。

在读已提交隔离级别下，每次普通 select 都会生成新的 Read View，因此同一事务中多次读取可能看到其他事务已提交的新数据。在可重复读隔离级别下，事务第一次一致性读时生成 Read View，后续复用，因此能保证多次读取结果一致。

MVCC 解决的是普通快照读的并发可见性问题。当前读，例如 `select ... for update`、update、delete，会读取最新版本并加锁。理解快照读和当前读的区别，有助于排查为什么 select 看到旧数据而 update 又能影响最新数据。

## 锁机制

MySQL InnoDB 常见锁包括行锁、表锁、间隙锁、Next-Key Lock、意向锁等。行锁锁住索引记录，粒度小、并发高；表锁锁住整张表，并发较差。InnoDB 的行锁是基于索引实现的，如果更新条件没有走索引，可能扫描大量记录并加更多锁。

间隙锁锁住索引记录之间的间隙，主要用于防止幻读。Next-Key Lock 是记录锁和间隙锁的组合。可重复读隔离级别下，范围查询加锁可能锁住一段范围，导致其他事务无法插入这个范围内的新记录。

避免锁问题的关键是让更新和删除语句命中合适索引，控制事务时间，按固定顺序访问资源，避免用户交互或远程调用放在事务中。排查锁等待可以查看 `show processlist`、`information_schema.innodb_trx`、`innodb_locks`、`innodb_lock_waits` 或 MySQL 8 的 performance_schema。

## 慢 SQL 定位

慢 SQL 定位通常从接口耗时、数据库监控、慢查询日志和 APM 链路开始。找到慢 SQL 后，先看 SQL 频率和耗时，再用 EXPLAIN 分析执行计划。重点关注 type、possible_keys、key、rows、filtered、Extra。

type 反映访问方式，常见从好到差包括 const、eq_ref、ref、range、index、ALL。ALL 表示全表扫描，不一定绝对错误，但在大表高频查询中通常需要优化。Extra 中 Using filesort 表示需要额外排序，Using temporary 表示使用临时表，Using index 表示覆盖索引。

优化前要确认业务语义，不能为了使用索引改变查询结果。很多慢 SQL 的根因不是缺索引，而是查询范围过大、分页过深、返回字段太多、统计口径不合理、长事务阻塞或数据倾斜。

## SQL 改写

SQL 改写的目标是让数据库更容易使用索引、减少扫描行数、减少回表和排序。常见做法包括避免 `select *`，只查询必要字段；把函数计算移到参数侧；把前缀模糊查询改为可走索引的形式；分页使用游标；大 IN 拆分批次；复杂统计改为离线或异步汇总。

例如 `where date(create_time) = '2026-06-20'` 会对列做函数计算，可能导致索引失效。可以改写为 `where create_time >= '2026-06-20 00:00:00' and create_time < '2026-06-21 00:00:00'`。又如深分页 `limit 100000, 20` 可以改为 `where id > last_id order by id limit 20`。

对于教学数据统计，如课程提问次数、错题数量、正确率、活跃度，如果每次实时扫描大量明细表，性能可能不稳定。可以根据业务频率设计统计表或缓存，把高频聚合结果异步计算。

## 索引设计原则

索引设计要从查询场景出发。高频过滤字段、连接字段、排序字段和分组字段是索引候选。联合索引列顺序通常遵循等值条件在前、范围和排序在后、区分度高且稳定的字段优先。覆盖索引可以减少回表，但索引字段不能无限增加。

索引不是越多越好。每个索引都会增加写入和更新成本，占用磁盘空间，也会增加优化器选择成本。重复索引和长期不用的索引应清理。对于低选择性字段，单独建索引可能效果不明显，但放在联合索引前缀中结合其他字段可能有价值。

课程学习助手中，`agent_qa_record(user_id, create_time)` 适合查用户问答历史，`learning_event(course_id, event_time)` 适合查课程学习活跃度，`answer_record(course_id, correct, create_time)` 适合按课程统计正确率和错题。
