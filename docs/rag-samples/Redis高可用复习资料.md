# Redis 高可用复习资料

## 主从复制

Redis 主从复制用于把主节点数据同步到从节点。主节点负责写入，从节点可以承担读请求，也可以作为故障切换的备份。主从复制可以提升读能力和可用性，但默认情况下写操作仍然集中在主节点。

复制流程通常包括全量复制和增量复制。从节点第一次连接主节点，或复制积压缓冲区中找不到缺失数据时，会触发全量复制。主节点生成 RDB 快照并发送给从节点，从节点加载后继续接收后续命令。网络短暂断开后，如果复制偏移量仍在积压缓冲区中，可以进行增量复制，只同步缺失命令。

主从复制是异步的，因此存在复制延迟。如果主节点刚写入数据还没同步到从节点，从节点读取可能是旧数据。对于强一致要求高的业务，不能简单把读请求全部打到从节点。

## 哨兵模式

Redis Sentinel 用于监控主从节点并自动故障转移。哨兵会定期检查主节点和从节点是否可用。如果多个哨兵认为主节点不可用，会选举一个哨兵作为领导者，由它完成故障转移：选择一个从节点提升为新主节点，让其他从节点复制新主节点，并通知客户端新的主节点地址。

哨兵判断主观下线和客观下线。单个哨兵认为节点不可用是主观下线；达到多数哨兵共识后是客观下线。这个设计可以减少单点误判。哨兵本身也应部署多个实例，避免哨兵单点故障。

哨兵模式适合单主多从场景，能解决主节点故障后的自动切换问题。但它不解决单主写入瓶颈，也不天然支持数据分片。如果数据量很大或写压力很高，需要考虑 Redis Cluster。

## Redis Cluster

Redis Cluster 通过分片把数据分布到多个主节点上。它使用 16384 个哈希槽，每个 key 根据 CRC16 计算槽位，槽位分配给不同主节点。每个主节点可以配置从节点用于故障转移。

Cluster 的优点是支持水平扩展，数据量和吞吐可以随节点增加而提升。缺点是客户端需要支持集群协议，跨 slot 多 key 操作受限，例如某些 mget、事务、Lua 脚本只能在同一个 slot 内执行。可以使用 hash tag 让相关 key 落到同一个 slot，例如 `{course}:1:info` 和 `{course}:1:stat`。

Cluster 故障转移依赖节点间 gossip 通信。如果某个主节点不可用，它的从节点可以被提升为新主节点。为了保证可用性，每个主节点至少应有一个从节点，并合理分布在不同机器上。

## 缓存一致性

缓存一致性是指数据库和 Redis 中同一份数据在更新后的可见结果尽量一致。常见方案是先更新数据库，再删除缓存。为什么不是先删缓存再更新数据库？因为先删缓存后，如果更新数据库还没完成，其他请求可能读旧数据库并把旧值重新写入缓存。

先更新数据库再删除缓存也不是绝对完美。如果删除缓存失败，缓存里仍然可能保留旧值。因此可以增加重试机制、消息队列补偿或订阅 binlog 异步删除。对于一致性要求不高的数据，可以设置较短 TTL，让旧缓存自然过期。

延迟双删是一种补偿方案：先删除缓存，更新数据库，再延迟一段时间删除一次缓存。它可以降低并发读写导致旧值回填的概率，但不能提供严格一致性。设计时要结合业务对一致性的要求、缓存命中率和更新频率。

## 热点 Key

热点 key 指访问量远高于其他 key 的缓存数据，例如热门课程详情、排行榜、首页配置、秒杀商品。热点 key 可能导致单个 Redis 节点压力过高，甚至造成网络带宽、CPU 或连接数瓶颈。

解决热点 key 可以从缓存副本、本地缓存、拆分 key 和限流降级入手。对于读多写少的热点数据，可以在应用本地使用 Caffeine 做二级缓存，减少 Redis 压力。对于大 value，可以拆成多个小 key，避免一次传输过大。对于极端热点，可以通过多副本 key 分散读取，例如 `hot:course:1:0` 到 `hot:course:1:9`。

热点 key 排查可以看 Redis 的 bigkeys、hotkeys、命令统计、慢日志和应用访问日志。发现热点后，不要只扩容 Redis，还要看业务是否可以降低访问频率、合并请求或在前端/网关层缓存。

## 大 Key

大 key 指 value 很大或集合元素很多的 key。它会造成网络传输慢、Redis 阻塞、删除耗时长、主从复制压力大和内存碎片。常见大 key 包括超大 Hash、List、Set、ZSet 或存储大 JSON 的 String。

处理大 key 的方式包括拆分、分页、压缩和异步删除。比如一个课程下所有学习行为不应放在一个 List 中无限增长，而应写入数据库或按日期拆分。删除大 key 时可以使用 UNLINK 异步删除，避免 DEL 阻塞主线程。

大 key 发现可以使用 `redis-cli --bigkeys`、SCAN 分批扫描、内存分析工具和监控报警。生产环境不要直接使用 KEYS 全量扫描，因为它会阻塞 Redis。

## Redis 慢查询

Redis 是单线程执行命令的模型，单个慢命令会阻塞后续命令。慢查询日志可以记录执行时间超过阈值的命令。常见慢命令包括大集合操作、复杂 Lua 脚本、一次返回大量数据、KEYS、SMEMBERS 大集合等。

优化 Redis 慢查询要减少单次命令处理的数据量。可以使用 SCAN 替代 KEYS，使用 SSCAN/HSCAN/ZSCAN 分批遍历集合，避免一次取出全部元素。对于排行榜、计数、会话等场景，要控制 key 的生命周期和集合大小。

如果 Redis 慢查询和应用接口超时同时出现，需要结合应用日志、Redis 命令统计、网络延迟、连接池配置和机器负载判断。不要只看 Redis 本身，客户端连接池耗尽也可能表现为 Redis 请求慢。
