# Redis 复习资料

## Redis 常用数据结构

Redis 是基于内存的高性能键值数据库，常用于缓存、计数、排行榜、分布式锁、消息队列和会话存储。Redis 的基础数据类型包括 String、Hash、List、Set、Sorted Set，后来还提供 Bitmap、HyperLogLog、GEO、Stream 等扩展结构。String 是最常用的数据结构，可以保存字符串、整数、JSON 文本或序列化对象，适合缓存对象、计数器、验证码和短期令牌。Hash 适合保存对象字段，例如用户资料中的姓名、年龄、状态等，读取单个字段时比整体反序列化对象更方便。List 是双端链表结构，支持从左右两侧插入和弹出，可用于简单队列、时间线和最新消息列表。Set 是无序去重集合，适合标签、点赞用户集合、共同好友和去重统计。Sorted Set 在 Set 的基础上给每个元素增加 score，常用于排行榜、延迟队列和按权重排序的场景。

Bitmap 本质上是对 String 的位操作，适合签到、活跃状态和布尔标记统计。HyperLogLog 用较小内存估算基数，适合 UV 统计，但结果是近似值。GEO 用于地理位置存储和附近的人查询。Redis Stream 是 Redis 5.0 引入的日志型消息结构，支持消息 ID、消费者组、ACK、Pending List 等机制，比 List 更适合构建轻量级消息队列。选择数据结构时要看访问模式：如果只做简单键值读取，用 String；如果对象字段需要局部更新，用 Hash；如果需要顺序消费，用 List 或 Stream；如果要去重，用 Set；如果要排序，用 Sorted Set。

## 缓存穿透

缓存穿透指请求查询的数据在缓存和数据库中都不存在。攻击者或异常流量如果持续请求不存在的 key，会导致每次请求都绕过缓存打到数据库，数据库压力急剧上升。典型例子是请求不存在的用户 ID、商品 ID 或课程 ID。解决思路有三类。第一类是缓存空值，当数据库确认不存在时，在 Redis 中写入一个短 TTL 的空对象或特殊标记，下次请求可以直接命中缓存。空值 TTL 不宜太长，否则真实数据后来创建时可能短时间读不到。第二类是布隆过滤器，将合法 ID 集合提前放入过滤器，请求进来先判断 key 是否可能存在，不可能存在则直接拒绝或返回空结果。布隆过滤器有误判但无漏判，适合读多写少、数据集合相对稳定的场景。第三类是参数校验和限流，例如检查 ID 范围、格式、租户权限，并对异常来源做频率限制。

缓存穿透排查时可以关注数据库慢查询、Redis 未命中率、接口中不存在数据的比例。如果某类 key 的请求量很高但命中率很低，就需要判断是否存在穿透风险。工程实现中要注意空值缓存的 key 命名、序列化格式和过期时间，并避免把权限不足和数据不存在混在一起缓存，防止用户 A 的无权限结果影响用户 B。

## 缓存击穿

缓存击穿指一个热点 key 在过期瞬间，大量并发请求同时发现缓存不存在，然后一起访问数据库。它和缓存穿透不同，击穿的数据本身存在，只是热点 key 过期导致瞬时流量打到数据库。常见场景包括首页配置、热门课程、秒杀活动详情、排行榜头部数据等。解决方案包括互斥锁、逻辑过期和热点 key 不过期。

互斥锁方案是在缓存未命中后，只有一个线程获得锁并回源数据库重建缓存，其他线程等待、重试或返回旧值。锁可以用 Redis 的 SET key value NX EX 实现，释放锁时要校验 value，避免误删其他线程的锁。逻辑过期方案是不让 Redis key 真正过期，而是在 value 中保存 expireTime。请求发现逻辑过期后，先返回旧数据，再由后台线程异步刷新缓存。这种方案牺牲短时间强一致性，换取高可用和低延迟。热点 key 不过期适合变化很少的数据，但需要在数据变更时主动删除或更新缓存。

## 缓存雪崩

缓存雪崩指大量缓存 key 在同一时间失效，或者 Redis 集群不可用，导致流量集中打到数据库。它的影响范围比击穿更大，往往会造成数据库连接耗尽、接口超时和级联故障。预防缓存雪崩可以从过期时间、系统降级和高可用三个层面处理。首先，缓存 TTL 增加随机抖动，避免同一批 key 同时过期。例如基础 TTL 为 30 分钟，再随机加 0 到 5 分钟。其次，对热点数据进行预热，服务启动或活动开始前提前加载缓存。再次，Redis 应部署主从、哨兵或集群，避免单点故障。接口层还应增加限流、熔断、降级和本地缓存，在 Redis 不可用时保护数据库。

缓存雪崩排查时要看 Redis 连接错误、超时比例、key 过期时间分布、数据库 QPS 和线程池堆积情况。如果大量接口同时变慢，且 Redis 命中率突然下降，要优先怀疑雪崩或 Redis 故障。

## 分布式锁

Redis 分布式锁常用于防止多个服务实例同时执行同一段关键逻辑，例如重复发奖、重复提交、库存扣减和定时任务抢占。基础命令是 SET lockKey requestId NX EX seconds。NX 表示 key 不存在时才设置成功，EX 表示设置过期时间，避免业务进程崩溃后锁永远不释放。requestId 通常使用 UUID，释放锁时通过 Lua 脚本先判断 value 是否等于自己的 requestId，再删除 key，这样可以避免线程 A 锁过期后线程 B 获得锁，线程 A 又误删线程 B 的锁。

分布式锁要关注锁过期时间、业务执行时间和可重入问题。如果业务耗时可能超过锁 TTL，需要续期机制，例如 Redisson 的 watchdog。锁粒度也很重要，粒度太大会降低并发，粒度太小又可能无法保护共享资源。对于强一致金融场景，仅靠 Redis 锁通常不够，还需要数据库唯一索引、事务、状态机或幂等表兜底。

## RocketMQ 与 Redis Stream 的区别

RocketMQ 是专门的分布式消息中间件，适合高吞吐、可靠投递、延迟消息、事务消息、顺序消息、消费重试和消息堆积治理。它有 NameServer、Broker、Producer、Consumer 等组件，运维复杂度较高，但在生产级异步解耦、削峰填谷和事件驱动场景中更稳定。Redis Stream 是 Redis 内置的数据结构，提供追加日志、消费者组、ACK 和 Pending List，适合轻量级消息、低延迟通知、小规模异步任务和已有 Redis 基础设施的项目。

二者的关键差异在于定位和可靠性能力。RocketMQ 的消息存储、消费重试、死信队列、堆积监控和水平扩展能力更完整，适合核心业务链路。Redis Stream 使用简单，读写延迟低，但它依赖 Redis 内存和持久化配置，面对大量消息堆积、复杂消费拓扑和跨机房容灾时不如专业 MQ。选型时可以按重要性判断：核心交易、奖励发放、统计事件等建议使用 RocketMQ；简单通知、低风险异步处理、学习行为轻量记录可以考虑 Redis Stream。

## RDB 和 AOF

Redis 持久化主要有 RDB 和 AOF 两种方式。RDB 是快照持久化，会在某个时间点把内存数据生成 dump 文件。优点是文件紧凑、恢复速度快、适合备份和灾难恢复；缺点是两次快照之间的数据可能丢失。RDB 生成时通常通过 fork 子进程完成，数据量很大时会带来 fork 开销和写时复制内存压力。

AOF 是追加日志持久化，会把写命令追加到 AOF 文件。它的数据安全性通常高于 RDB，可以配置 always、everysec、no 三种刷盘策略。everysec 是常用折中方案，最多丢失约 1 秒数据。AOF 文件会随着写入变大，因此 Redis 提供 AOF rewrite 机制，用更短的命令重写当前数据状态。AOF 恢复速度一般慢于 RDB，但数据更完整。生产环境常同时开启 RDB 和 AOF：RDB 用于快速备份，AOF 用于降低数据丢失风险。对于纯缓存场景，可以接受丢数据时持久化要求较低；对于分布式锁、消息队列、会话等场景，要认真评估持久化和主从复制延迟带来的影响。
