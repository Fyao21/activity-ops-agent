# MySQL 索引复习资料

## B+ 树索引

MySQL InnoDB 最常用的索引结构是 B+ 树。B+ 树是一种多路平衡搜索树，所有叶子节点位于同一层，叶子节点之间通过链表连接，非叶子节点只保存索引键和子节点指针。与二叉树相比，B+ 树每个节点可以存放更多 key，树高更低，磁盘 I/O 次数更少。数据库查询通常以页为单位读取数据，InnoDB 默认页大小为 16KB，一个页中可以放多个索引项，因此 B+ 树非常适合磁盘存储。

B+ 树适合等值查询、范围查询、排序和前缀匹配。例如 `where id = 10` 可以沿树路径快速定位叶子节点；`where age between 18 and 25` 可以先定位起点，再沿叶子链表顺序扫描；`order by create_time` 如果命中索引顺序，也可以减少 filesort。B+ 树不适合在索引列上做复杂函数计算后的匹配，也不适合低选择性字段单独建索引，例如性别字段只有两个值时，优化器可能认为全表扫描更划算。

## 聚簇索引

InnoDB 的表数据按照主键索引组织，主键索引就是聚簇索引。聚簇索引的叶子节点保存整行数据，因此通过主键查询可以直接拿到完整记录，不需要再次回表。一个 InnoDB 表只能有一个聚簇索引，因为数据行只能按一种顺序物理组织。如果表定义了主键，InnoDB 使用主键作为聚簇索引；如果没有主键，会选择一个唯一非空索引；如果仍然没有，会生成隐藏 row_id。

主键设计会影响聚簇索引效率。自增主键通常顺序写入，页分裂少，插入性能稳定。随机 UUID 主键会导致数据插入位置分散，容易造成页分裂、页利用率下降和索引膨胀。如果业务需要全局唯一 ID，可以考虑雪花算法、趋势递增 ID 或将随机 ID 作为唯一二级索引，而不是直接作为聚簇主键。聚簇索引还有一个重要影响：所有二级索引叶子节点都会保存主键值，因此主键越大，二级索引占用空间越大。

## 非聚簇索引

非聚簇索引也叫二级索引或辅助索引。InnoDB 的二级索引叶子节点不保存完整行数据，而是保存索引列和主键值。通过二级索引查询时，如果查询字段不在索引中，需要先在二级索引中找到主键，再回到聚簇索引查询整行，这个过程叫回表。例如有索引 `idx_user_id(user_id)`，执行 `select * from orders where user_id = 1` 时，先通过 user_id 找到订单主键，再用主键查询整行订单。

为了减少回表，可以使用覆盖索引。覆盖索引指查询需要的字段都在同一个索引中，例如 `select id, user_id from orders where user_id = 1`，如果 `idx_user_id` 中包含 user_id 和主键 id，就不需要回表。覆盖索引可以显著降低随机 I/O，但不能为了覆盖所有查询无限增加索引字段，因为索引越多，写入成本越高，占用空间越大，优化器选择也更复杂。

## 联合索引

联合索引是在多个列上建立的索引，例如 `index idx_course_user_time(course_id, user_id, create_time)`。联合索引的列顺序非常关键，通常应把区分度高、过滤条件稳定、经常用于等值查询的列放在前面，把范围列或排序列放在后面。联合索引可以同时支持过滤、排序和覆盖查询。例如查询某课程下某用户最近答题记录，条件为 `course_id = ? and user_id = ? order by create_time desc`，建立 `(course_id, user_id, create_time)` 往往比单列索引更有效。

联合索引不是多个单列索引的简单替代。多个单列索引在某些情况下可以通过 index merge 合并，但性能通常不如一个设计合理的联合索引。设计联合索引时要结合真实 SQL，而不是只看字段。常见原则是优先覆盖高频慢查询，避免为低频查询建立过多复合索引。

## 最左前缀原则

最左前缀原则是联合索引使用的核心规则。对于索引 `(a, b, c)`，查询条件可以使用 `a`，也可以使用 `a and b`，还可以使用 `a and b and c`。如果查询只有 `b` 或 `b and c`，通常无法有效使用这个联合索引的有序结构。范围查询也会影响后续列的使用，例如 `where a = 1 and b > 10 and c = 3` 中，a 和 b 可以用于索引定位，但 c 往往不能继续用于精确定位，只可能在索引条件下推中辅助过滤。

最左前缀并不要求 SQL 条件书写顺序完全一致，优化器会重排等值条件。但索引列的定义顺序不能随意。设计索引时要分析 where、order by、group by 中的列组合。如果查询经常按 `course_id` 过滤，再按 `create_time` 排序，那么 `(course_id, create_time)` 比 `(create_time, course_id)` 更符合访问路径。

## 索引失效

索引失效指 SQL 表面上有索引，但优化器没有使用，或只使用了一部分。常见原因包括在索引列上使用函数或表达式，例如 `where date(create_time) = '2026-06-19'`，这会破坏索引有序性，应改写为范围查询。隐式类型转换也会导致索引失效，例如字符串字段 `phone` 使用数字条件 `where phone = 13800138000`。模糊查询如果以通配符开头，例如 `like '%abc'`，无法利用 B+ 树前缀有序性。对索引列使用 `or`，如果两边条件不能都有效走索引，也可能退化为全表扫描。使用 `not equal`、`not in`、低选择性字段、返回大量数据时，优化器也可能选择全表扫描。

判断索引是否失效不能只凭经验，需要使用 `explain`。重点看 type、possible_keys、key、rows、filtered、Extra 等字段。type 从好到差大致为 const、eq_ref、ref、range、index、ALL。Extra 中出现 Using index 表示覆盖索引，Using filesort 表示需要额外排序，Using temporary 表示使用临时表。rows 估算扫描行数过大时，需要考虑索引设计、统计信息和 SQL 改写。

## SQL 优化

SQL 优化的第一步是定位慢 SQL，可以通过慢查询日志、APM、数据库监控和接口耗时分析找到高频或高耗时语句。第二步使用 explain 分析执行计划，确认访问类型、扫描行数、是否回表、是否排序和是否使用临时表。第三步根据业务语义优化 SQL 和索引。常见优化包括只查询必要字段，避免 `select *`；分页深度很大时使用基于主键或时间的游标翻页；把函数计算移到参数侧；避免在大表上无条件排序；批量写入代替循环单条写入；合理拆分复杂 SQL；对热点统计使用汇总表或异步计算。

索引优化要控制数量。每个索引都会增加 insert、update、delete 的维护成本。更新索引列时，数据库需要调整 B+ 树结构。一般应删除长期不用的重复索引和冗余索引，例如已有 `(a, b)` 时，单独的 `(a)` 可能是冗余的，但如果 `(a)` 更小且被高频覆盖查询使用，也可能保留。优化还要关注事务和锁。长事务会持有锁和 undo 版本，影响并发和 purge；缺少索引的更新语句可能扫描大量记录并扩大锁范围。最终目标不是让每条 SQL 都使用索引，而是在正确性、响应时间、吞吐量和维护成本之间取得平衡。
