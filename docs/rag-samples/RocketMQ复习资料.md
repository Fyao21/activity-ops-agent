# RocketMQ 复习资料

## RocketMQ 基本架构

RocketMQ 是分布式消息中间件，常用于异步解耦、削峰填谷、事件驱动、最终一致性和延迟任务。它的核心组件包括 NameServer、Broker、Producer 和 Consumer。NameServer 负责保存 Topic 路由信息，Broker 负责消息存储和投递，Producer 负责发送消息，Consumer 负责消费消息。

RocketMQ 的 NameServer 是轻量级注册中心，多个 NameServer 之间通常不直接通信。Broker 会定期向 NameServer 注册 Topic 路由信息，Producer 和 Consumer 从 NameServer 获取路由后直接和 Broker 通信。Broker 通常可以配置主从，提升可用性和读能力。

在课程学习助手项目中，RocketMQ 主要用于文档索引、学习行为记录和答题统计。上传文档后，接口不直接调用耗时的文档切分和向量化，而是发送文档索引消息；消费者异步调用 Python RAG 服务完成索引。

## Topic、Tag 和 ConsumerGroup

Topic 是消息的一级分类，通常表示一类业务事件。Tag 是 Topic 下的二级过滤条件，用于区分更细的业务类型。ConsumerGroup 表示一组具有相同消费逻辑的消费者实例，同一个 ConsumerGroup 内的多个实例会共同分摊消息。

设计 Topic 时不能过细，也不能过粗。过细会增加运维成本，过粗会导致消费者过滤复杂。课程学习助手中可以使用 `edu_knowledge_index_topic` 表示文档索引任务，Tag 使用 `DOC_INDEX`；使用 `edu_learning_event_topic` 表示学习行为，Tag 包括 `QUESTION`、`ANSWER`、`VIEW_COURSE`、`UPLOAD_DOC`；使用 `edu_answer_stat_topic` 表示答题统计任务。

ConsumerGroup 要和消费语义绑定。如果两个消费者逻辑不同，应使用不同 ConsumerGroup；如果只是同一逻辑的水平扩展，应使用同一个 ConsumerGroup。错误复用 ConsumerGroup 可能导致某些消息被错误消费者消费，或者消费进度相互影响。

## 生产者发送消息

RocketMQ 支持同步发送、异步发送和单向发送。同步发送会等待 Broker 返回结果，适合核心业务消息；异步发送通过回调拿结果，适合高吞吐场景；单向发送不关心结果，适合日志类低风险消息。

在业务接口中发送消息时，要注意消息体字段要稳定，最好包含业务唯一标识、事件时间和必要上下文。例如文档索引消息应包含 `documentId`、`courseId`、`filePath`、`fileName`。学习行为消息应包含 `userId`、`courseId`、`eventType`、`eventTime`、`messageKey`。

如果消息发送失败，接口应该如何处理取决于业务重要性。对于文档索引，文档元数据已经写库但消息发送失败会导致文档一直待处理，可以通过本地消息表或定时扫描待处理文档补偿。对于学习行为，短时间丢失可能影响统计准确性，也应至少记录日志和告警。

## 消费者处理消息

消费者收到消息后应先做参数校验，再执行业务逻辑。处理成功后正常返回，RocketMQ 认为消费成功；如果抛出异常，RocketMQ 会按策略重试。不要在消费失败时吞掉异常，否则 Broker 会认为消息已经成功，后续不会再投递。

消费者代码要保持幂等，因为消息系统通常只能保证至少一次投递，不能保证绝对只投递一次。文档索引可以通过文档状态判断是否已经处理成功；学习行为可以通过 `messageKey` 唯一键防重复；答题统计可以通过 `answerRecordId` 防重复统计。

消费逻辑不宜过重。耗时下游调用要设置超时，失败要记录清楚原因。对于文档索引，如果 Python RAG 服务不可用，消费者应抛出异常让 RocketMQ 重试，同时可以把失败原因写入文档表，方便前端或管理员查看。

## 消费重试和死信队列

RocketMQ 消费失败后会进行重试。并发消费模式下，消息失败会进入重试队列，延迟一段时间后再次投递。超过最大重试次数后，消息会进入死信队列。死信队列不是问题解决本身，而是告诉系统“这条消息自动处理已经多次失败，需要人工或补偿程序介入”。

生产环境需要监控消费失败率、重试消息数、消费堆积和死信队列数量。如果死信队列持续增长，说明业务逻辑、数据状态或下游依赖存在问题。例如文档索引死信可能是文件路径不存在、Python 服务不可用、Embedding 模型下载失败或向量库写入失败。

处理死信消息时，要先定位失败原因，修复后再重新投递或执行补偿逻辑。不能简单把死信消息全部丢弃，否则可能造成数据不一致。

## 顺序消息

顺序消息适合要求同一业务键下事件按顺序处理的场景，例如订单创建、支付、发货、完成。RocketMQ 可以通过 MessageQueueSelector 或业务 key 让同一个业务对象的消息进入同一个队列，从而保证局部顺序。

并不是所有业务都需要顺序消息。课程学习助手中的文档索引、学习行为和答题统计大多不要求严格顺序，只要求最终被处理。过度使用顺序消息会降低并发能力，因为同一队列内的消息需要串行处理。设计时要区分“必须有序”和“结果最终一致即可”。

如果某个业务要求状态流转，例如文档状态从待处理到处理中再到成功或失败，可以在数据库中使用状态机约束，而不是完全依赖 MQ 顺序。

## 事务消息和本地消息表

RocketMQ 事务消息用于解决本地事务和消息发送之间的一致性问题。基本流程是先发送半消息，然后执行本地事务，本地事务成功后提交消息，失败后回滚消息。如果 RocketMQ 不确定事务状态，会回查生产者。

本地消息表是另一种常见方案。业务事务中同时写业务表和消息表，事务提交后由后台任务扫描未发送消息并投递 MQ，发送成功后更新消息状态。它的优点是实现直观、可控性强，缺点是需要维护消息表和补偿任务。

课程学习助手当前可以先使用普通消息满足练习项目要求。如果要提升严谨性，文档索引任务可以引入本地消息表：上传文档和写待发送消息在同一个事务中完成，后台任务负责可靠投递。
