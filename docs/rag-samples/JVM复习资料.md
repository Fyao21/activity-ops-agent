# JVM 复习资料

## JVM 内存结构

JVM 运行时内存可以分为线程私有区域和线程共享区域。线程私有区域包括程序计数器、Java 虚拟机栈和本地方法栈。程序计数器记录当前线程正在执行的字节码行号，线程切换后可以恢复执行位置。Java 虚拟机栈保存方法调用栈帧，每个栈帧包含局部变量表、操作数栈、动态链接和方法返回地址。局部变量表中保存基本类型、对象引用和 returnAddress。栈空间不足或递归过深可能导致 StackOverflowError，线程过多或栈内存申请失败可能导致 OutOfMemoryError。

线程共享区域包括堆和方法区。堆是对象实例主要分配区域，也是垃圾回收最关注的区域。现代 JVM 通常把堆按代际思想划分为新生代和老年代，新生代又包括 Eden 和 Survivor 区。大部分对象朝生夕死，先在 Eden 分配，Minor GC 后仍存活的对象会进入 Survivor，多次存活或大对象可能晋升到老年代。方法区保存类元数据、常量、静态变量和即时编译后的代码等。在 JDK 8 之后，方法区的实现主要是元空间，使用本地内存。运行时常量池、直接内存、线程栈和 JNI 相关内存也可能成为内存问题来源。排查 JVM 内存问题时不能只看堆，还要关注元空间、直接内存、线程数量和容器限制。

## 类加载机制

类加载是 JVM 把 class 字节码加载到内存，并转化为可使用类型的过程。完整流程包括加载、验证、准备、解析和初始化。加载阶段通过类的全限定名获取二进制字节流，生成 Class 对象。验证阶段检查字节码是否合法，防止破坏 JVM 安全。准备阶段为静态变量分配内存并设置默认值，例如 static int a 在准备阶段是 0，而不是代码中写的具体值。解析阶段把常量池中的符号引用替换为直接引用。初始化阶段执行类构造器 `<clinit>`，为静态变量赋真实值并执行 static 代码块。

类初始化有明确触发条件，例如 new 对象、访问静态字段、调用静态方法、反射调用、初始化子类时先初始化父类、启动主类等。理解类加载机制有助于排查静态变量初始化顺序、类找不到、版本冲突和热部署问题。类加载器通常包括启动类加载器、扩展类加载器或平台类加载器、应用类加载器以及自定义类加载器。不同类加载器加载的同名类在 JVM 中可以被认为是不同类型，这也是一些 ClassCastException 和插件隔离问题的根源。

## 双亲委派

双亲委派模型指类加载器收到加载请求后，先把请求交给父加载器处理，父加载器无法加载时，子加载器才尝试加载。这个机制的主要目的是保证 Java 核心类库的安全和唯一性。例如用户自己写了一个 `java.lang.String`，正常情况下不会覆盖 JDK 自带的 String，因为请求会先委托给启动类加载器。双亲委派还能避免同一个核心类被重复加载，保持类型体系稳定。

双亲委派不是绝对不可打破。JDBC、SPI、应用服务器、OSGi、热部署框架和一些插件系统会使用线程上下文类加载器或自定义加载策略，让父加载器可以反向使用子加载器可见的类。Tomcat 为了隔离不同 Web 应用，也会让每个应用使用独立类加载器。面试或排查问题时要说明：双亲委派是默认模型，解决核心类安全和重复加载问题；在需要模块隔离、插件化或 SPI 扩展时，可能会被有控制地打破。

## 垃圾回收算法

垃圾回收首先要判断对象是否存活。常见方法有引用计数和可达性分析。JVM 主流使用可达性分析，从 GC Roots 出发，沿引用链能到达的对象视为存活。GC Roots 包括虚拟机栈中引用的对象、方法区静态属性引用的对象、常量引用的对象、本地方法栈 JNI 引用的对象、活跃线程对象和同步锁持有对象等。

常见垃圾回收算法包括标记清除、复制、标记整理和分代收集。标记清除先标记存活对象，再清理未标记对象，缺点是会产生内存碎片。复制算法把内存分成两块，每次只使用一块，回收时把存活对象复制到另一块，适合存活率低的新生代，但空间利用率较低。标记整理在标记后把存活对象向一端移动，再清理边界外内存，适合老年代，能减少碎片。分代收集基于对象生命周期差异，新生代使用复制算法，老年代使用标记清除或标记整理。

常见垃圾收集器包括 Serial、Parallel、CMS、G1、ZGC 和 Shenandoah。G1 把堆划分成多个 Region，按收益优先回收，目标是可预测停顿。ZGC 和 Shenandoah 更关注低延迟，通过并发标记、并发整理和读屏障等技术降低停顿时间。选择 GC 时要结合吞吐、延迟、堆大小和业务特点。

## 常见 OOM 原因

OOM 不只是一种问题。Java heap space 通常表示堆内存不足，可能是对象创建过多、缓存无上限、集合未清理、批量查询太大或内存泄漏。Metaspace OOM 表示类元数据占用过多，常见于动态生成类、频繁热部署、反射代理框架滥用或类加载器泄漏。Direct buffer memory 表示直接内存不足，常见于 Netty、NIO、文件传输和堆外缓存。Unable to create new native thread 表示无法创建新线程，可能是线程池无限增长、系统线程数限制、每个线程栈过大或容器资源不足。GC overhead limit exceeded 表示 JVM 大部分时间都在 GC，但回收效果很差。

常见内存泄漏来源包括静态集合持续持有对象、ThreadLocal 使用后未 remove、监听器或回调未注销、连接或流未关闭、缓存缺少过期策略、大对象日志堆积、批处理一次性加载过多数据。排查时要结合错误类型、GC 日志、堆转储和业务变更，而不是只简单调大 `-Xmx`。调大内存可能缓解症状，但如果存在泄漏，问题会在更晚时间再次出现。

## Full GC 排查思路

Full GC 是对整个堆或老年代进行回收的重大事件，通常会带来明显停顿。排查 Full GC 首先要收集证据，包括 GC 日志、JVM 参数、堆大小、老年代使用率、对象晋升速率、应用 QPS、接口耗时和发布变更记录。开启 GC 日志后，可以观察 Full GC 发生频率、每次停顿时长、回收前后内存变化。如果 Full GC 后老年代下降明显，说明对象可以被回收，可能是瞬时流量、大批量任务或参数设置不合理；如果 Full GC 后老年代几乎不下降，说明大量对象仍被引用，需要重点怀疑内存泄漏或缓存过大。

第二步是分析对象来源。可以使用 jmap、jcmd、MAT、VisualVM、Arthas 等工具生成 heap dump，查看 Dominator Tree、Histogram 和 GC Roots，找出占用内存最多的对象及其引用链。对于线上服务，导出 dump 会有停顿和磁盘压力，应在低峰期或故障副本上执行。第三步检查代码和配置，例如是否存在无界队列、无界缓存、大分页查询、一次性加载文件、批量导出、ThreadLocal 泄漏、连接池配置过大等。第四步根据原因处理：限制批量大小，增加缓存上限和过期时间，优化对象生命周期，调整新生代和老年代比例，升级 GC 收集器，或拆分大任务。

Full GC 排查要避免只看单点指标。一次 Full GC 可能由 System.gc、元空间扩容、老年代空间不足、大对象分配失败、晋升失败或并发模式失败触发。需要结合触发原因、内存曲线和业务流量判断。稳定系统的目标不是完全没有 Full GC，而是 Full GC 频率低、停顿可接受、回收后内存能回到健康水位。
