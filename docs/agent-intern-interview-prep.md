# Agent 开发实习工程师面试准备文档

本文档用于准备 Agent 开发实习工程师方向面试，内容围绕当前项目“智能课程学习助手 Agent 平台”展开，重点覆盖项目介绍、RAG、Text-to-SQL、Hybrid Agent、工具调用、后端工程化和常见追问。

---

## 1. 项目一句话介绍

我做的是一个面向课程学习场景的智能课程学习助手 Agent 平台，整体采用 SpringBoot 后端服务 + Python FastAPI Agent 服务的双服务架构。Java 后端负责用户、课程、知识库文档、题目、答题、错题、学习行为、Redis 缓存和 RocketMQ 异步任务；Python Agent 负责 RAG 知识库问答、Text-to-SQL 学习数据分析、Hybrid Agent 混合分析、FAISS 向量检索和大模型调用。

这个项目主要解决三个问题：

1. 学生查课程资料和课后答疑效率低。
2. 教师查询学习数据需要写 SQL。
3. 课程资料内容和学习行为数据相互割裂，难以综合分析学生薄弱点。

---

## 2. 面试中的项目介绍模板

如果面试官让你介绍项目，可以按这个顺序说：

### 2.1 背景

传统课程学习系统一般只提供课程资料、题目和答题记录，学生遇到问题时还需要自己翻资料，教师想分析学生学习情况也经常依赖固定报表或手写 SQL。所以我做了一个智能课程学习助手 Agent 平台，把 RAG、Text-to-SQL 和 Hybrid Agent 接入到课程学习业务里。

### 2.2 架构

系统拆成两个服务：

- SpringBoot 后端：负责课程、知识库、题目、答题、错题、学习行为、问答记录、Redis 缓存和 RocketMQ 消息。
- Python FastAPI Agent：负责文档切分、Embedding、FAISS 检索、RAG 问答、SQL 生成、安全校验和大模型总结。

Java 和 Python 之间通过 HTTP 调用。这样做的原因是 Java 更适合业务系统、权限、数据库事务和 MQ；Python 在 LangChain、Embedding、FAISS 和大模型生态上更成熟。

### 2.3 核心能力

项目里有三类 Agent 能力：

1. RAG：学生基于课程资料提问。
2. Text-to-SQL：教师用自然语言查询学习数据。
3. Hybrid Agent：同时结合课程资料和数据库学习数据，生成薄弱点分析和复习建议。

### 2.4 工程化设计

我还做了几块工程化处理：

- SQL Guard：只允许 SELECT，禁止危险 SQL、多语句和敏感字段访问。
- course_id 检索隔离：避免不同课程资料混在一起。
- RocketMQ 异步索引：上传文档后异步切分和向量化，避免阻塞上传接口。
- 幂等处理：文档状态判断、messageKey 去重、answerRecordId 去重。
- 问答记录落库：保存问题、路由类型、生成 SQL、检索上下文、回答和错误信息，方便排查。

## 3. 项目亮点总结

面试时可以主动讲这些亮点：

1. Java + Python 双服务解耦  
   Java 做业务系统，Python 做 Agent 能力，职责清晰，后续可以独立升级 Agent 服务。

2. RAG 降低幻觉  
   不直接让模型凭空回答，而是先检索课程资料片段，再让模型基于上下文回答。

3. course_id 做课程级隔离  
   检索时只查当前课程资料，避免不同课程内容混入回答，也为权限隔离打基础。

4. Text-to-SQL 降低教师查数门槛  
   教师可以问“最近 7 天每门课程提问次数”“Redis 课程错题最多的知识点”等问题。

5. SQL Guard 做安全兜底  
   模型生成 SQL 后必须校验，避免误删数据、查询敏感字段或返回过大结果集。

6. Hybrid Agent 支持综合分析  
   对“结合课程资料和答题情况分析薄弱点”这类问题，同时走 RAG 和 SQL。

7. RocketMQ 异步解耦  
   文档索引、学习行为、答题统计从主流程拆出，提升接口响应速度。

8. 可排障设计  
   Agent 问答记录、文档索引状态、错误信息都落库，方便复盘模型行为和排查问题。

## 4. 高频项目追问与回答

### Q1：你的 RAG 流程怎么做？

A：

我的 RAG 流程是：

1. 用户上传课程资料。
2. Java 后端保存文件和 `knowledge_document` 记录。
3. 发送 RocketMQ 文档索引消息。
4. Consumer 调用 Python `/rag/index`。
5. Python 读取文档，按段落和长度切分。
6. 调用 Embedding 模型生成向量。
7. 向量写入 FAISS。
8. 用户提问时，根据 `course_id` 过滤当前课程资料。
9. TopK 召回相关片段。
10. 拼接 Prompt，让大模型基于上下文回答。

---

### Q2：为什么要用 course_id 做隔离？

A：

因为不同课程的资料可能都在同一个向量库里。如果不做隔离，学生问 Redis 的问题时可能召回 MySQL 或 JVM 的资料，导致回答混乱。

`course_id` 隔离有三个价值：

1. 提升检索准确性。
2. 避免不同课程资料混入回答。
3. 为后续权限控制打基础，比如学生只能查询自己选修课程的资料。

---

### Q3：文档怎么切分？chunk 多大？overlap 怎么设置？

A：

当前项目使用文本切分器按段落、换行、中文句号、分号、逗号等分隔符递归切分。默认 chunk size 是 500，overlap 是 80。

这样设置的考虑是：

- chunk 太小，语义不完整，模型拿不到完整上下文。
- chunk 太大，检索粒度粗，也会占用更多上下文窗口。
- overlap 可以避免知识点刚好被切断，比如定义在上一个 chunk，解释在下一个 chunk。

后续如果资料更复杂，可以引入按标题层级切分、父子分块、按 Markdown 标题切分，或者在召回后加 Rerank。

---

### Q4：RAG 检索不到内容怎么办？

A：

当前会返回“知识库中未找到相关信息”，不让模型硬编。

后续可以继续优化：

1. 增加 query rewrite，把用户问题改写成更适合检索的关键词。
2. 调整 topK 和相似度阈值。
3. 增加多路召回，比如关键词召回 + 向量召回。
4. 引入 Rerank，提高召回片段排序质量。
5. 引导用户补充课程、章节或更具体的问题。

---

### Q5：如何规避 RAG 幻觉？

A：

我主要从四层控制：

1. 检索层：使用 course_id 限制资料范围。
2. Prompt 层：要求模型只能基于给定课程资料回答。
3. 兜底层：检索不到内容时返回“知识库中未找到相关信息”。
4. 记录层：保存 retrieved_context 和 answer，后续可以复盘模型是否基于资料回答。

如果继续优化，可以增加引用来源展示、答案可信度评分和离线评测集。

---

### Q6：Text-to-SQL 怎么做？

A：

Text-to-SQL 由 Python Agent 负责。流程是：

1. 用户输入自然语言问题。
2. Agent 根据问题和允许访问的表结构生成 SQL。
3. SQL 进入 SQL Guard 校验。
4. 校验通过后执行查询。
5. 查询结果交给大模型总结成自然语言。
6. Java 后端保存问题、生成 SQL、查询结果和回答。

典型问题包括：

- 统计最近 7 天每门课程提问次数。
- 查询 Redis 课程错题最多的知识点。
- 统计某门课程平均正确率。

---

### Q7：Text-to-SQL 怎么保证安全？

A：

我没有直接执行模型生成的 SQL，而是加了 SQL Guard。主要限制包括：

1. 只允许单条 SELECT。
2. 禁止 INSERT、UPDATE、DELETE、DROP、ALTER、TRUNCATE、CREATE 等危险语句。
3. 禁止多语句执行。
4. 禁止访问 password 字段。
5. 限制只能访问白名单表。
6. 没有 LIMIT 时自动补 `LIMIT 100`。

这样可以把模型生成 SQL 的风险控制在只读、有限、可控的范围内。

---

### Q8：Text-to-SQL 准确率怎么提升？

A：

可以从几方面优化：

1. 给模型更清晰的表结构说明和字段语义。
2. 在 Prompt 里加入常见业务口径，比如正确率、错题数、提问次数怎么计算。
3. 限制可访问表，减少模型选择错误表的概率。
4. SQL 执行失败时，让模型基于错误信息修复一次。
5. 建立典型问题到 SQL 的 few-shot 示例。
6. 做离线评测集，统计 SQL 执行成功率和结果准确率。

当前项目已经做了表白名单、业务口径提示、SQL Guard 和失败重试修复。

---

### Q9：Hybrid Agent 怎么判断走 RAG 还是 SQL？

A：

当前用问题路由器按关键词判断：

- 统计类问题走 SQL，例如“数量、正确率、排名、最近、平均、活跃度”。
- 解释类问题走 RAG，例如“什么是、解释、原理、总结、资料、文档”。
- 综合分析类问题走 Hybrid，例如“结合、根据、分析、建议、薄弱点、掌握情况”。

Hybrid 的流程是先检索课程资料，再查询学习数据，最后让模型综合输出学习分析。

---

### Q10：如果 Hybrid Agent 路由错了怎么办？

A：

当前可以通过问答记录复盘 route_type、generated_sql、retrieved_context 和 answer，发现路由错误后调整关键词规则。

后续可以优化：

1. 规则路由 + LLM 意图分类结合。
2. 对低置信度问题返回澄清问题。
3. 给路由器加 few-shot 示例。
4. 建立路由评测集，统计 sql/rag/hybrid 分类准确率。
5. 允许前端或调用方显式指定 route_type。

---

### Q11：Agent 工具调用失败怎么办？

A：

我会按工具类型处理：

- SQL 工具失败：捕获异常，尝试基于错误信息修复 SQL；仍失败则返回友好提示，并保存失败记录。
- RAG 工具失败：提示知识库暂不可用或未找到相关内容，不让模型编造。
- Python 服务失败：Java 侧捕获调用异常，返回业务错误，不暴露底层堆栈。
- MQ 消费失败：记录日志并抛异常，让 RocketMQ 重试；多次失败后后续接入 DLQ 巡检和补偿。

通用原则是：参数校验、异常捕获、有限重试、降级兜底、日志记录和结果落库。

---

### Q12：为什么 Java 和 Python 服务要解耦？

A：

Java 更适合做业务接口、权限控制、数据库事务、Redis、RocketMQ 和系统工程；Python 更适合 LangChain、Embedding、FAISS、大模型调用和 Agent 编排。

解耦的好处是：

1. 职责清晰。
2. AI 能力可以独立迭代。
3. Java 后端不需要直接依赖复杂 AI 生态。
4. Python Agent 可以单独扩容、部署和替换模型。
5. 后续 RAG、Text-to-SQL、Hybrid 可以独立升级，不影响主业务系统。

---

## 5. Agent 基础高频题

### Q1：什么是 Agent？

A：

Agent 可以理解为具备一定自主决策能力的智能应用。它不只是调用一次大模型，而是可以根据用户目标进行任务理解、规划、调用工具、观察结果，并根据结果继续下一步动作。

常见组成部分包括：

- LLM：负责理解、推理和生成。
- Tools：外部工具，比如搜索、数据库、RAG、代码执行。
- Memory：保存短期上下文和长期历史。
- Planner：任务拆解和步骤规划。
- Executor：执行工具调用。
- Observer：接收工具结果。

---

### Q2：ReAct 是什么？

A：

ReAct 是 Reasoning + Acting 的结合。模型不是直接给最终答案，而是在推理过程中决定调用工具，观察工具返回，再继续推理。

典型链路是：

```text
Thought -> Action -> Observation -> Thought -> Final Answer
```

它适合需要工具调用的问题，比如查数据库、检索知识库、调用接口。优点是过程可解释，缺点是链路更长、延迟更高，也更依赖工具调用稳定性。

---

### Q3：Function Calling 是什么？

A：

Function Calling 是大模型根据用户问题和工具 Schema，输出结构化工具调用参数的能力。模型不会直接执行函数，而是告诉系统应该调用哪个函数、传什么参数，真正执行由业务系统完成。

工具 Schema 一般包括：

- 工具名称。
- 工具描述。
- 参数字段。
- 参数类型。
- 必填项。
- 字段说明。

Function Calling 的关键是 Schema 要清晰，参数要校验，工具执行要有异常处理和权限控制。

---

### Q4：Tool、Skill、MCP 有什么区别？

A：

可以这样理解：

- Tool：具体可调用工具，比如查数据库、检索知识库、调用天气接口。
- Skill：更高层的能力封装，可能包含一组工具和一套操作流程。
- MCP：一种工具接入协议，用于让模型或 Agent 以统一方式发现和调用外部工具、资源和上下文。

面试中不用讲得太底层，重点说清楚：工具调用要有 Schema、权限、参数校验、错误处理和可观测性。

---

### Q5：上下文怎么管理？

A：

上下文分为短期上下文和长期记忆。

- 短期上下文：当前会话中的最近几轮消息，可以放在请求上下文或 Redis 中。
- 长期记忆：用户历史问题、偏好、学习记录、错题记录，可以存数据库或向量库。

需要注意用户隔离，不能让不同用户的上下文互相污染。Key 设计上可以使用 `agent:session:{userId}:{courseId}`。上下文过长时可以做摘要压缩，只保留关键信息。

---

### Q6：如何避免不同用户上下文互相污染？

A：

主要靠隔离：

1. Redis key 加 userId 和 courseId。
2. 数据库记录保存 user_id 和 course_id。
3. RAG 检索按 course_id 过滤。
4. 查询前做权限校验。
5. 每次请求只加载当前用户和当前课程相关上下文。

不能把全局变量或单例对象作为用户上下文存储，否则并发请求下容易串数据。

## 6. RAG 进阶高频题

### Q1：文档切分有哪些策略？

A：

常见策略包括：

1. 固定长度切分：实现简单，但可能切断语义。
2. 按段落切分：适合 Markdown、课程资料、文章。
3. 按标题层级切分：保留章节结构，适合技术文档。
4. 递归切分：优先按大分隔符切，再按小分隔符切。
5. 父子分块：小 chunk 用于检索，大 chunk 用于回答。

当前项目使用递归切分，按段落、换行和标点优先切分，并设置 overlap。

---

### Q2：Embedding 模型怎么选？

A：

主要看语言、领域、效果、成本和部署方式。

- 中文课程资料优先选择中文或多语言 embedding 模型。
- 如果数据敏感或希望降低 API 成本，可以使用本地 embedding。
- 如果追求效果和维护简单，可以使用云端 embedding API。
- 需要通过评测集比较召回率、相关性和延迟。

当前项目开发阶段支持本地 embedding，降低外部依赖和调用成本。

---

### Q3：FAISS 是什么？为什么用它？

A：

FAISS 是向量相似度检索库，适合本地快速搭建向量检索能力。它可以把文档向量保存起来，用户提问时把问题向量化，再找最相似的 TopK 文档片段。

使用 FAISS 的原因是：

1. 本地开发简单。
2. 不依赖外部向量数据库。
3. 适合中小规模课程资料。
4. 能快速验证 RAG 链路。

如果文档规模更大，可以考虑 Milvus、Qdrant、Elasticsearch 向量检索或云向量数据库。

---

### Q4：TopK 怎么设置？

A：

TopK 太小可能漏掉关键上下文；TopK 太大可能带入噪声，也会增加 Prompt 长度和模型成本。

当前项目默认 topK 是 4。这个值适合课程资料问答的初始版本。后续可以根据问题类型动态调整，比如概念解释 topK 小一点，综合总结 topK 大一点。也可以先召回较多片段，再用 Rerank 选出更相关的片段。

---

### Q5：Rerank 有什么用？

A：

向量召回主要看语义相似度，但不一定完全符合用户问题。Rerank 会对候选片段重新排序，把更相关的片段放到前面。

常见做法是：

1. 向量库先召回 top 20。
2. Rerank 模型重新打分。
3. 取 top 3 到 top 5 拼 Prompt。

Rerank 可以提升答案准确性，但会增加一次模型调用或推理成本。

---

### Q6：RAG 效果怎么评估？

A：

可以从检索和生成两层评估：

检索层指标：

- Recall@K：正确资料是否出现在 TopK。
- MRR：正确结果排名是否靠前。
- 命中率：是否检索到相关片段。

生成层指标：

- 答案是否基于资料。
- 是否出现幻觉。
- 是否完整回答问题。
- 用户满意度。

工程上可以建立一批标准问题和标准引用片段，定期跑评测，比较切分策略、Embedding 模型、topK、Rerank 的效果。

## 7. 后端工程化高频题

### Q1：Redis 在项目里怎么用？

A：

Redis 主要用于：

1. 登录态缓存。
2. 课程详情热点缓存。
3. Agent 会话上下文缓存预留。
4. 热点问答缓存预留。

课程详情属于读多写少数据，查询时先查 Redis，未命中再查 MySQL，更新课程后删除缓存。

---

### Q2：RocketMQ 在项目里怎么用？

A：

RocketMQ 用于异步任务：

1. 文档索引：上传资料后异步调用 Python RAG 建索引。
2. 学习行为：提问、答题、查看课程、上传资料异步落库。
3. 答题统计：提交答案后发送统计消息，后续可扩展课程统计和知识点统计。

这样可以把耗时任务从主流程拆出去，提高接口响应速度，也方便失败重试。

---

### Q3：如何处理 MQ 重复消费？

A：

不同任务使用不同幂等键：

- 文档索引：判断 `knowledge_document.status`，已成功则跳过；重新索引前删除旧 chunk。
- 学习行为：使用 `messageKey` 唯一键防重复写入。
- 答题统计：使用 `answerRecordId` 防重复统计。

核心思想是消息可以重复投递，但业务结果不能重复生效。

---

### Q4：RocketMQ 消息堆积怎么办？

A：

先定位原因：

1. 消费者是否挂了。
2. 下游 Python 或数据库是否变慢。
3. 消费逻辑是否有异常重试。
4. 消费线程数是否不足。
5. 单条消息处理是否太慢。

处理方式：

1. 扩容消费者实例。
2. 优化消费逻辑和下游调用超时。
3. 临时降级非核心任务。
4. 对失败消息进入 DLQ 后补偿处理。
5. 增加堆积监控和告警。

---

### Q5：MySQL 索引怎么设计？

A：

围绕查询场景设计：

- `agent_qa_record(user_id, create_time)`：查用户问答历史。
- `learning_event(course_id, event_time)`：查课程活跃度。
- `answer_record(course_id, correct, create_time)`：统计课程正确率和错题。
- `knowledge_document(course_id, status)`：查课程资料和处理状态。

索引不是越多越好，要平衡查询性能和写入成本。

## 8. 安全与稳定性问题

### Q1：Agent 生成 SQL 或代码时怎么做安全控制？

A：

当前项目只做 Text-to-SQL，不执行代码。SQL 安全控制包括：

1. 只允许 SELECT。
2. 禁止危险关键字。
3. 禁止多语句。
4. 禁止敏感字段。
5. 表白名单。
6. 自动 LIMIT。
7. 生产环境建议使用只读数据库账号。

如果是代码执行类 Agent，还需要沙箱、资源限制、网络隔离、文件系统隔离和超时控制。

---

### Q2：如何防 Prompt Injection？

A：

RAG 场景中，用户上传的文档可能包含“忽略之前指令”这类攻击内容。防护方式包括：

1. 系统 Prompt 明确要求只把文档当资料，不当指令。
2. 对用户输入和文档内容做角色隔离。
3. 工具调用前做权限和参数校验。
4. 敏感操作不能只靠模型决定。
5. SQL、文件、网络访问都要有白名单和安全策略。

当前项目的 SQL Guard 就是工具安全兜底的一部分。

---

### Q3：LLM 并发太高怎么办？

A：

可以从几层处理：

1. 接口限流，避免瞬时请求打爆模型服务。
2. 热点问答缓存，重复问题直接返回缓存。
3. RAG 检索和 SQL 查询结果缓存。
4. 异步化非实时任务。
5. 模型网关统一做超时、重试、熔断和降级。
6. 根据场景使用小模型处理分类、路由、改写，大模型处理最终回答。

---

### Q4：端到端延迟怎么优化？

A：

RAG/Agent 延迟通常来自检索、数据库查询、模型调用和网络。优化方式包括：

1. 缓存课程资料检索结果或热点问答。
2. 减少 topK 或压缩上下文。
3. 使用 Rerank 时控制候选数量。
4. SQL 查询加索引。
5. 模型调用设置合理超时。
6. 前端用 SSE 流式输出，减少用户等待感。
7. 对文档索引这类任务使用 MQ 异步处理。

## 12. 最后提醒

这个项目面试时不要讲成普通 CRUD 项目，要突出“Agent 工程化落地”：

- 大模型不是单独存在的，而是接入了课程业务。
